# 部署与数据迁移

全新部署使用空数据目录自行注册，或执行 `python tools/init_demo.py` 创建唯一虚构示例账号。升级已有部署时，使用该部署最新的完整数据，不使用源码副本中的示例数据替换正式数据。

## 数据目录

日记本默认使用 `日记本/current/data/`：

| 路径 | 保存内容 |
| --- | --- |
| `user-data/userN/diary-data/diary.db` | `logs` 保存每日记录，`user_state` 保存在途任务与待提升属性 |
| `user-data/userN/diary-data/资产变化.txt` | 总资产及变化记录 |
| `user-data/userN/ui_settings.json`、`welcome_audio.json` | 界面与欢迎音频设置 |
| `auth/users.json`、`user-data/user_map.json` | 账号密码哈希及用户目录映射，必须配套保留 |
| `music-data/` | 音乐和欢迎音频 |
| `oss_backup_config.json`、`.backup-runtime/` | OSS 部署配置、调度状态与最近成功时间 |
| `.session-secret`、`.subservices/` | 登录签名秘密、工作区凭证等运行状态 |

认知工作区默认使用 `认知工作区/cognitive_workspace/data/`，包含 `workspace.sqlite3`、`calls/`、`backups/`、`users/` 及运行状态。它独立于日记数据目录，日记 OSS 快照不自动包含这部分数据。

## 升级步骤

1. 保存旧代码、两套服务的身份配置、正式数据位置及环境变量配置。
2. 停止会写入数据的日记及工作区进程，将两套完整 `data/` 复制到替换范围之外。在线备份时，SQLite 使用在线备份 API，并协调其他文件的一致性；不单独复制仍在写入的数据库而丢弃 WAL。
3. 在独立新目录部署配套代码和 `identity/`，保持日记本与工作区的相对结构。演练使用正式数据的一致副本，关闭 OSS 备份，隔离正式凭证和模型调用。
4. 检查账号与原 `userN` 对应，最近日记、资产、任务及工作区对话正确，SQLite `PRAGMA integrity_check` 返回 `ok`。
5. 切换前再次停写，使用最终数据副本整体替换新版本的测试数据，不混合不同来源的数据库。保持原账号文件、映射、备份配置和 `.backup-runtime/`。
6. 为实际运行账户设置环境变量，启动服务并检查登录、相互跳转及备份状态。正式备份配置启动时可能触发当天补备份；不要以 `--backup-now` 作为普通迁移检查。

升级时保留完整 `data/`，不仅是单个 `diary.db`。环境变量不会随目录复制。`DIARY_DATA_ROOT` 支持指定日记数据路径；工作区路径覆盖方法见其 README。新旧版本不可同时写入同一套正式数据。

## 数据兼容与回退

对于兼容的原有 `logs` 表，日记程序首次读取时补建 `user_state`，将旧 `待提升属性.txt` 仅导入一次，并初始化缺失的在途任务为空。已有内容保留，不自动合并两份数据库，也不自动修复任意旧版表结构。

“计划与摘要”的显示继承沿用现有 `logs.plan_summary` 列，无需新增数据库结构，不改变已保存历史。

上线尚未产生新写入时，可停止新版本并恢复切换前代码及数据；已有新写入时先完整保存新数据，再安排回退。日记 OSS 快照格式、范围与版本保留规则没有因开源整理而改变。
